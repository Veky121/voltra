## What the original recipe actually supplies

`palworld/egg-palworld-proton.json` (canonical SHA256 `9f05c0426a38a31883379ee5d39323634bf8427a990f59b85406d39cc0b0e15c`) has 12 explicit controls, Windows Steam app2394010, WindowsServer settings, public-lobby/performance/player/name/password/admin flags, parser-based implicit configuration support, RCON-backed stdin and `shutdown 5`. Its defining extra capability is UE4SS Lua/C++/Blueprint mod loading, not simply Windows Palworld running under Proton. Native `.pak`/LogicMods, custom UE4SS mods/settings/load order and operator files must remain available through Files. Existing typed parser/control work must stay intact.

The installer downloads a mutable egg-repository `winmm.dll`, selects the upstream latest stable `UE4SS_` asset and unzips it beside `PalServer-Win64-Shipping.exe`. That upstream latest still resolves to v3.0.1 from February2024. The resulting legacy layout includes **both** extra `winmm.dll` and the archive's `dwmapi.dll`, root `UE4SS.dll`, root settings and root Mods. Blindly repeating this operation overwrites operator loader settings and bundled mod files. A modern UE4SS archive has a different nested layout; blindly mixing it with legacy files risks loading two copies.

## Compatibility constraints and recommended path

The legacy winmm is a UE4SS injection proxy, not evidence of an Ultimate ASI loader. Its source-like behavior forwards the Windows system winmm and loads root UE4SS.dll. PE imports require MSVCP140, VCRUNTIME140 and VCRUNTIME140_1/UCRT; legacy UE4SS additionally imports MSVCP140_ATOMIC_WAIT. Modern UE4SS also imports MSVCP140_CODECVT_IDS, bcryptprimitives and Wine-supported Windows APIs. The existing pinned Proton/prefix must genuinely supply these dependencies; the plan must not run an unrelated redistributable installer or accept agreements automatically. Do not promise compatibility from PE layout alone.

The current Palworld-specific maintainer's fixed September2026 release adds its required MemberVariableLayout and fixes FText behavior, explicitly warns about changed C++ mod ABI, and prohibits simultaneously loading Workshop and manually installed UE4SS. The maintainer is primary for its fork, not the Palworld publisher. Generic stable3.0.1 compatibility with current Palworld is not established. The proposed modern candidate preserves the original mod-loader capability, but **does not preserve binary ABI of every old C++ mod**. Keep the exact legacy profile/import path available with honest build constraints; never silently migrate it or run vanilla instead.

Recommended acceptance candidate after root approval: the fixed modern maintainer archive using its own `dwmapi.dll` and `ue4ss/` layout, without the unrelated opaque legacy winmm in the active loader chain. This is an explicit reviewed loader migration preserving the mod feature, not a claim that legacy winmm and the modern DLL may be safely combined. Preserve original custom mods and settings; root must approve the migration policy. An alternative is a source-built modern winmm proxy if retaining that exact loader filename is required. Until one path is reviewed and natively demonstrated, keep the existing unavailable reason.

## Proposed deterministic installation transaction

1. Use the current signed node job/Windows-platform installation path and shared secure publication, not a new UI or transport. Restrict the dependency choice to a reviewed manifest revision. Download only allowlisted immutable OSS identities into per-server `.voltra/palworld-modloader/cache/<sha256>` with digest/size checks. Never execute files during extraction.
2. Validate ZIP paths before writing: no absolute/drive/UNC paths, backslashes/traversal, Windows reserved/trailing-dot names, links/reparse entries, duplicate case-folded paths or non-regular members. Bound ≤512 members, ≤64MiB total unpacked, ≤32MiB per file, and allowlist the reviewed member layout. Validate AMD64 PE headers/core imports and exact individual hashes. Keep archive/source notices. Stage under a confined private sibling directory before publication.
3. Inventory root and nested UE4SS, winmm/dwmapi/xinput proxies, Workshop-managed UE4SS, settings, MemberVariableLayout, both Mods paths, mods.txt, enabled.txt and load-order files. Never delete/move unknown loader copies, operator mods, signatures, settings or native saves automatically. Conflicting/unreceipted active loaders or unsupported mixed layouts fail with exact actionable paths. There is no vanilla fallback or loader-disable-on-error option.
4. Immutable release material and license/manifest live privately under `.voltra/palworld-modloader/releases/<manifest-hash>`. Publish only the necessary checked loader/core copies at the real executable-relative paths required by UE4SS; do not use unsafe symlinks or hard links to mutable operator state. Treat settings/mod files as operator-owned after first seed. Existing files are adopted only if exact reviewed bytes or explicit operator-selected existing installation; changed/unknown files are preserved and block replacement.
5. Fresh installs seed bundled mod files/settings only when absent. Preserve every custom Lua/C++/Blueprint mod and native `.pak`/LogicMods. Preserve enabled flags and mods.txt/order exactly. For explicit legacy→modern migration, make a full metadata-preserving backup and obtain a root-reviewed deterministic mapping first. The modern supported ModsFolderPath/ControllingModsTxt may point at an existing legacy tree without moving it, but relative-path semantics and dependency ordering require source/native proof. Do not merge two folders containing identically named mods or auto-enable bundled cheat/admin mods. No migration is implemented here.
6. Before mutating any owned target, journal original bytes/SHA/mode/timestamps or absent state, proposed digest and ownership. Securely publish the complete checked set while the owned server is stopped; write the committed receipt last. On error restore the exact previous committed set and metadata, remove only newly created owned leaves, retain failure evidence and leave unknown/operator files untouched. Startup requires a complete committed receipt and actual matching active-core hashes; interrupted journals require explicit recovery, never optimistic success.
7. Receipt includes exact manifest revision, artifact source URLs/asset IDs/hashes, source/license identities, active loader choice, Wine DLL override choice, relative managed files and prior ownership hashes, settings/mod inventory, game build/depot receipt, runtime identity and installation transaction outcome. Do not hash/log credential-bearing server config values into public diagnostics. Keep token/RCON control files private.
8. Keep current WindowsServer settings, original launcher flags, real password gates, RCON stdin and Shutdown5/save orchestration. Configure only the reviewed active proxy's required DLL override inside that server's private Wine environment. Do not globally edit Wine/system libraries or couple native Linux mode to UE4SS. Any missing loader/dependency/receipt fails before native game launch.
